Microbenchmark — Batch Scaling (Apple arm, 2026-06-01)

Throughput (img/s) vs batch size

Why latency curves matter: p50 per-image latency at each batch size reveals whether a model is compute-bound or memory-bound. A compute-bound model (YOLO, DINOv3) shows latency flat or slowly rising with batch — the GPU stays fully utilised at all sizes. A memory-bound model (RMBG, aesthetic predictor) plateaus quickly and latency rises sharply past the saturation point. The safe batch is chosen just before that inflection, and the bandit confirms it at runtime.

Scheduler — UCB Bandit Convergence

How the bandit works: Each model has several batch-size arms (e.g. batch=1, 4, 8, 16). On each pass the UCB (Upper Confidence Bound) algorithm picks an arm, balancing exploitation (use the highest-reward arm) with exploration (occasionally try others to confirm they're still worse). After each run it records a reward equal to achieved img/s divided by the profiled img/s baseline. The bar length shows mean reward per pull. The green bar is the dominant arm — the batch size with the highest mean reward. A reward of 1.0 means the live run matched the benchmark; above 1.0 means this machine outperformed it at that batch size.
